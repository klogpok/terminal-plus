# DevPanel — спецификация MVP

## Цель
Локальное приложение для члена команды без опыта в программировании. Он работает одновременно с несколькими репозиториями и должен запускать, останавливать и смотреть сервисы каждого репо, не открывая терминалы вручную. Отдельной кнопкой запускается Claude Code в нужном репо.

Целевая платформа: **Windows 10/11**. Пакетный менеджер: **pnpm**.

## Стек
- **Backend:** Node.js (LTS) + TypeScript, Fastify, WebSocket (`@fastify/websocket`).
- **Процессы:** `node-pty` (на Windows работает через ConPTY). Если установка падает из‑за отсутствия build tools, использовать форк с готовыми бинарниками (например, `@homebridge/node-pty-prebuilt-multiarch`). Проверить это первым делом.
- **Frontend:** Angular + `@xterm/xterm` + `@xterm/addon-fit`.
- **Конфиги:** YAML (`yaml`), валидация через `zod`.
- **Десктоп (позже):** Electron. Tauri не подходит, потому что требует Rust-бэкенда, а логика процессов и pty у нас на Node.
- Монорепо на pnpm:
  - `packages/core`: вся логика (конфиги, процессы, порты, статусы, логи). Не зависит от HTTP и Electron.
  - `packages/shared`: общие типы и контракт сообщений между фронтом и бэком.
  - `apps/server`: тонкая обёртка Fastify + WebSocket над `core` (веб-режим).
  - `apps/web`: Angular UI.
  - `apps/desktop`: Electron-обёртка (этап 6), использует тот же `core` и тот же `web`.

## Почему Angular
UI маленький, и технически хватило бы и более лёгкого фреймворка. Angular выбран потому, что команда его знает, а значит тулзу сможет поддерживать любой разработчик. Размер бандла неважен, потому что всё работает локально, а в Electron Angular работает без изменений.

Правила, чтобы фронт оставался простым:
- Только standalone-компоненты, без NgModules.
- Состояние на signals. Без NgRx и других state-менеджеров.
- Без тяжёлых UI-библиотек. Если у команды есть свой UI-кит, можно использовать его.
- Вся связь с бэкендом идёт через один сервис-адаптер (см. «Архитектура и переход на десктоп»).

## Архитектура и переход на десктоп
Приложение сразу проектируется так, чтобы веб-версия на localhost превратилась в десктопную почти без изменений.

- **`core` — чистый модуль.** Он экспортирует API вида `startService`, `stopService`, `restartService`, `startAll`, `stopAll`, `openTerminal`, `openClaude`, `writeToPty`, `resizePty`, `openFolder`, `listRepos`, `addRepo`, `removeRepo`, `relocateRepo`, `closeSession`, `shutdown`, а также события (`statusChanged`, `log`, `exit`, `configChanged`). Внутри нет ни Fastify, ни Electron.
- **Транспорт — отдельный слой.** В веб-режиме `apps/server` пробрасывает API и события `core` через WebSocket. В десктопе `core` работает в Electron main-процессе, и транспортом служит либо тот же WebSocket на 127.0.0.1, либо Electron IPC через preload.
- **Фронт не знает о транспорте.** В Angular есть один `BackendService` с интерфейсом `BackendTransport` и реализацией `WsTransport`, а в десктопе позже добавится `IpcTransport`. Компоненты работают только с `BackendService`.
- **В UI ничего браузерно-специфичного.** Открытие папки, запуск терминала и подобные действия всегда идут через бэкенд (`explorer.exe` и т.д.), а не через ссылки или API браузера. «Открыть в браузере» тоже делается через бэкенд (`start "" <url>` или `shell.openExternal` в Electron).
- **Контракт сообщений** (типы команд и событий) лежит в `packages/shared` и используется обеими сторонами.
- **Процессами владеет Сервер, а не UI** (см. [ADR-0001](docs/adr/0001-server-owns-processes.md)). Сервисы и Сессии живут, пока работает Сервер. Закрытие или перезагрузка вкладки браузера их не останавливает: при повторном подключении клиент получает текущее состояние и буферы. Одновременно может быть подключено несколько клиентов, все они равноправны: состояние общее, ввод из любого клиента идёт в pty, размер pty берётся от последнего resize.

Термины (Репо, Сервис, Сессия, Зомби и т.д.) определены в [GLOSSARY.md](GLOSSARY.md).

## Конфигурация

### Workspace (глобальный)
Файл `%APPDATA%\devpanel\workspace.yml`:
```yaml
repos:
  - name: Billing
    path: C:\dev\billing
    color: "#4f8cff"
  - name: Portal
    path: C:\dev\portal
    color: "#22c55e"
```
Добавлять и удалять репо можно из UI (выбор папки). Ручная правка файла не требуется.
- Репо определяется путём, поэтому одну папку нельзя добавить дважды. Имя по умолчанию берётся из имени папки и должно быть уникальным в Workspace: при дубле UI просит указать другое.
- Удаление Репо, в котором работают Сервисы или открыты Сессии: подтверждение («В Billing работают 2 сервиса и 1 сессия Claude — они будут остановлены»), затем остановка всего и удаление. Вместе с Репо удаляется его Локальный конфиг. Папка Репо не трогается.
- Если папки Репо нет (удалена, переименована, отключён диск), Репо остаётся в Workspace серым с пометкой «Папка не найдена» и кнопками «Указать новое расположение» (меняется путь, имя и цвет сохраняются) и «Удалить».

### Конфиг репо
Файл `.devpanel.yml` в корне репо (коммитится командой):
```yaml
services:
  - id: api
    name: API
    cmd: pnpm --filter @app/api dev
    cwd: .
    port: 3000
    url: http://localhost:3000
    healthUrl: http://localhost:3000/health   # необязательно
    readyPattern: "listening on"              # необязательно, regex по логу
    dependsOn: []
    env:
      NODE_ENV: development
  - id: web
    name: Frontend
    cmd: pnpm --filter @app/web dev
    port: 4200
    url: http://localhost:4200
    dependsOn: [api]
```

Конфиг репо пишут и коммитят разработчики. DevPanel в папку Репо ничего не пишет.

- Сервис без `port`, `healthUrl` и `readyPattern` допустим (например, `tsc --watch`).
- `id` сервисов и `port` уникальны в пределах файла (проверка через zod).
- `dependsOn` ссылается только на сервисы того же Репо.

### Автоопределение и Локальный конфиг (если `.devpanel.yml` нет)
- Если есть `pnpm-workspace.yaml`, пройти по пакетам и предложить скрипты `dev` / `start` / `serve` как сервисы вида `pnpm --filter <name> <script>`.
- Иначе предложить скрипты из корневого `package.json`.
- В UI показать предложенный список с галочками и кнопку «Сохранить конфиг». Она записывает **Локальный конфиг** в `%APPDATA%\devpanel\repos\<хэш пути репо>.yml` (формат как у `.devpanel.yml`), а не в Репо.
- Если в Репо есть `.devpanel.yml`, используется только он. Локальный конфиг игнорируется (без слияния), и UI предлагает его удалить.
- В MVP автоопределение и «Установить зависимости» поддерживают только pnpm. Репо на npm/yarn работают, если `cmd` задан вручную в `.devpanel.yml`.

### Изменение конфига во время работы
- DevPanel следит за файлом конфига (Конфига репо или Локального).
- Остановленные сервисы сразу получают новую версию.
- Запущенные сервисы работают со старой версией и помечены «Конфиг изменился — перезапустите». Сервис, удалённый из конфига, показывается до его остановки.
- Если новый YAML невалиден, на Репо показывается ошибка, и продолжает использоваться последний валидный конфиг.

## Запуск процессов на Windows (важно)
- Запускать через оболочку, потому что `pnpm` на Windows — это `pnpm.cmd`:
  `pty.spawn('cmd.exe', ['/d', '/s', '/c', service.cmd], { cwd, env, cols, rows })`.
- В env добавить `FORCE_COLOR=1`, чтобы сохранялись цвета.
- `cwd` резолвить через `path.resolve(repo.path, service.cwd)`.
- Если в Репо есть `pnpm-lock.yaml`, перед запуском проверить, что `pnpm` доступен (`where pnpm`). Если нет, показать понятную ошибку с подсказкой (`corepack enable` или установка pnpm).
- Если в pnpm-репо нет `node_modules`, предложить кнопку «Установить зависимости» (`pnpm install`).
- Терминал сервиса интерактивный: ввод с клавиатуры передаётся в pty (чтобы можно было ответить на вопрос dev-сервера или нажать горячую клавишу vite), resize синхронизируется.

## Остановка (самое важное на Windows)
`pty.kill()` на Windows НЕ гарантирует остановку дочерних процессов (node, vite, esbuild и т.д.). Порядок остановки:
1. Отправить `\x03` (Ctrl+C) в pty.
2. Подождать до 5 секунд.
3. Если процесс жив, выполнить `taskkill /PID <pty.pid> /T /F`.
4. После остановки проверить, что порт сервиса освободился. Если нет, найти PID по порту и предложить его завершить.

«Остановить всё» (для Репо или для всех Репо) останавливает только Сервисы. Сессии закрываются своими вкладками или при Выходе из DevPanel.

Выход из DevPanel — это остановка Сервера: кнопка «Выйти из DevPanel» в UI, закрытие консольного окна `.bat` или (в Electron) выход из приложения. Закрытие вкладки браузера Выходом не считается.

Защита от зомби:
- Хранить запущенные процессы (Сервисы и Сессии) в `%APPDATA%\devpanel\pids.json`: PID, время создания процесса, Репо, id сервиса или тип Сессии.
- При Выходе из DevPanel (`SIGINT`, `SIGTERM`, `SIGHUP`/закрытие консоли, `beforeExit`, кнопка «Выйти») останавливать все процессы.
- При старте Сервера проверять `pids.json`. Зомби — это процесс, у которого совпали и PID, и время создания (иначе PID уже переиспользован чужим процессом, и трогать его нельзя). Найденные Зомби показать по-человечески («Сервис API из Billing остался с прошлого запуска») и предложить их убить.

## Порты
- Занятость порта определяется по таблице LISTEN-сокетов ОС на **любом** адресе (127.0.0.1, ::1, 0.0.0.0, ::), а не пробным `listen` на 127.0.0.1: Vite и Node 17+ часто слушают `::1`. Источник — `netstat -ano -p TCP` и `-p TCPv6` (быстрее PowerShell). Оттуда же берётся PID владельца, а имя процесса — через `tasklist /FI "PID eq <pid>"`.
- Тот же механизм служит сигналом Готовности «порт начал слушаться».
- Если порт держит наш сервис из другого Репо: «Порт 3000 занят сервисом API из репо Billing» и кнопка «Остановить его и запустить наш».
- Если порт держит Зомби: «Порт 3000 занят сервисом API из Billing, оставшимся с прошлого запуска» и та же кнопка.
- Если чужой процесс: «Порт 3000 занят процессом node.exe (PID 1234)» и кнопка «Завершить и запустить наш» (с подтверждением).
- После нажатия кнопки освобождаем порт, ждём, пока он станет свободен, и продолжаем запуск нашего сервиса.

## Статусы сервиса
`stopped` → `starting` → `running` → `stopping` → `stopped`, а также `unhealthy`, `crashed`, `exited`.
- **Готовность** (`starting` → `running`) наступает по первому из сработавших критериев: `readyPattern`, ответ `healthUrl` (поллинг каждую секунду), порт начал слушаться. Если ни один критерий не задан, сервис становится `running`, когда процесс проживёт ~3 с.
- `unhealthy`: процесс жив, но Готовность не наступила за 120 с. Процесс не убиваем, проверки продолжаются реже (раз в 5 с), и при успехе статус меняется на `running`. Показать «Запущен, но не отвечает».
- Проверки (health, порт, pattern) работают только в `starting` и `unhealthy`. После `running` статус меняется только при выходе процесса или по «Стоп».
- `crashed`: ненулевой код выхода, если пользователь не нажимал «Стоп». Показать код выхода и последние 30 строк лога.
- `exited`: код выхода 0, если пользователь не нажимал «Стоп» (разовая команда или dev-сервер вышел сам). Показать «Завершился сам» и последние строки лога, но не как ошибку.
- Автоперезапуска после `crashed` нет: показываем причину и кнопку «Запустить снова».
- `dependsOn` задаёт только порядок старта. При старте сервиса сначала запускаются его зависимости, и он ждёт их `running`. Если зависимость стала `crashed`/`exited`/`unhealthy`, зависящий сервис не стартует и объясняет причину. Остановка или падение зависимости на уже запущенные зависящие сервисы не влияет.

## Логи
- Кольцевой буфер ~10 000 строк на Сервис и на Сессию, только в памяти, без файлов. При Выходе из DevPanel буферы теряются.
- При перезапуске Сервиса буфер сохраняется, и в него добавляется разделитель «── перезапуск 14:32 ──», чтобы осталась видна причина прошлого падения.
- При открытии вкладки (и после переподключения клиента) сначала отдаётся буфер, затем поток.
- Кнопки «Очистить», «Копировать всё», поиск по логу (xterm search addon).

## Claude Code
- Кнопка «Claude Code» на каждом репо открывает интерактивную вкладку-терминал: `pty.spawn('cmd.exe', ['/d','/s','/c','claude'], { cwd: repo.path })`.
- Ввод с клавиатуры передаётся в pty, resize синхронизируется (addon-fit → `pty.resize`).
- Перед запуском проверить, что `claude` установлен (`where claude`). Если нет, показать понятное сообщение.
- Можно открывать несколько сессий на одно репо.
- Дополнительно кнопка «Терминал» открывает обычный `cmd.exe` или PowerShell в папке репо.
- Одна вкладка соответствует одной Сессии. Закрытие вкладки завершает Сессию, а если процесс ещё жив, сначала спрашивается подтверждение. Если процесс завершился сам, вкладка остаётся с пометкой «Сессия завершена». После перезагрузки страницы открытые Сессии восстанавливаются вместе с буфером.

## UI
- **Левая панель:** список репо (цветная полоса, имя, текущая git-ветка через `git rev-parse --abbrev-ref HEAD`, обновлять раз в 10 с). Внутри сервисы со статус-точкой (🟢 running, 🟡 starting/stopping, 🔴 crashed, ⚪ stopped) и кнопками ▶ ■ ⟳.
- **Заголовок репо:** кнопки «Запустить всё», «Остановить всё», «Claude Code», «Терминал», «Открыть папку» (`explorer.exe <path>`).
- **Правая часть:** вкладки (логи сервисов и сессии Claude Code). Цвет вкладки совпадает с цветом репо, чтобы не путать репо между собой.
- Кнопка «Открыть в браузере» у сервисов с `url`.
- **Сверху:** «Остановить всё во всех репо» (только Сервисы) и «Выйти из DevPanel» (с подтверждением; останавливает всё, включая Сессии, и Сервер).
- Статус-точки: 🟠 unhealthy, ⚪ с пометкой «завершился сам» для exited. У сервиса с изменившимся конфигом пометка «перезапустите».
- Все ошибки показываются человеческим языком, технические детали скрыты под «Подробнее».
- Язык интерфейса — русский (тексты вынести в один файл, чтобы потом легко добавить английский).

## Безопасность
- Сервер слушает только `127.0.0.1` (так ещё и не появится запрос брандмауэра Windows).
- Команды берутся только из конфигов. API не принимает произвольную команду с фронтенда, кроме запуска `claude` и оболочки в папке известного репо.
- Проверять Origin у WebSocket (только `http://127.0.0.1:<port>` / `http://localhost:<port>`).
- **Ключ доступа.** Origin не защищает от локальных процессов (например, от npm-пакета внутри одного из сервисов), а API умеет запускать оболочку. Поэтому Сервер при старте генерирует случайный ключ, сохраняет его в `%APPDATA%\devpanel\` и открывает браузер на `http://127.0.0.1:7777/#t=<ключ>`. WebSocket без верного ключа отклоняется. В Electron с IPC ключ не нужен.

## Запуск для пользователя
- `start-devpanel.bat`: запускает собранный сервер (`node apps/server/dist/main.js`) и открывает браузер на `http://127.0.0.1:7777`.
- Положить ярлык на рабочий стол.
- Второй экземпляр приложения не запускать: если порт 7777 занят нашим сервером, просто открыть браузер (с Ключом доступа из файла). Вторая вкладка — нормальный равноправный клиент.
- Закрытие консольного окна `.bat` означает Выход из DevPanel: все процессы останавливаются.

## Этапы
1. **Каркас:** монорепо, сервер, чтение конфигов, start/stop одного сервиса через node-pty, корректная остановка через taskkill. *Проверить на реальном pnpm-проекте, что после «Стоп» не остаётся node.exe.*
2. WebSocket, статусы, буфер логов, UI со списком репо и вкладками xterm.
3. Проверка портов, `dependsOn`, health/ready, `crashed` с последними строками лога.
4. Вкладка Claude Code и терминал в папке репо.
5. Автоопределение сервисов из pnpm-workspace, добавление репо из UI, `.bat`-запуск.
6. **Десктоп на Electron:**
   - `apps/desktop`: main-процесс запускает `core`, окно грузит собранный `apps/web`.
   - **node-pty под Electron:** это нативный модуль, его нужно пересобрать под ABI Electron (`@electron/rebuild`) или взять сборку с готовыми бинарниками под Electron. Проверить на Windows первым шагом этапа.
   - Транспорт: оставить WebSocket на 127.0.0.1 или перейти на IPC (`IpcTransport` через preload с `contextIsolation: true`).
   - Трей (свернуть, «Остановить всё», выход), автозапуск с Windows (по желанию), один экземпляр (`app.requestSingleInstanceLock`).
   - При закрытии окна и выходе из приложения останавливать все процессы (`before-quit`).
   - Сборка установщика: `electron-builder` (NSIS) для Windows.

## Критерии готовности MVP
- Можно добавить 2+ репо и запустить их сервисы одновременно. Логи и статусы не смешиваются.
- «Стоп» убивает всё дерево процессов, а порт освобождается.
- При конфликте портов показывается понятное сообщение с кнопкой решения.
- Выход из DevPanel останавливает все процессы. Повторный запуск находит Зомби (по PID и времени старта) и предлагает их убить.
- Перезагрузка страницы не останавливает ни Сервисы, ни Сессии: после неё всё на месте вместе с логами.
- Claude Code запускается в нужном репо из одной кнопки и с ним можно работать интерактивно.
- `core` не импортирует ничего из Fastify или Electron, а Angular-компоненты не обращаются к WebSocket напрямую, только через `BackendService`.
